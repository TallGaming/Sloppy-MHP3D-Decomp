## Selected original bytes and corrected boundaries

The original `P_v00.ovl` image remains the frozen 1,024-byte entry 4590, SHA-256
`680fb098d6aedba108a88c59baa2eb2951aa6f6ffd8f6a13f444575f18f12a3c`.
Exactly three selected bodies receive semantic analysis:

| Role used for analysis | Range, exclusive end | Bytes | SHA-256 |

| Initialization target | `0x09E7D000..0x09E7D038` | 56 | `5b8f5c4a2ac23cef2737578c93d3f8df0e67233b9995062c4a0ce6361bb64ade` |

The initial 132/92-byte disassembly windows extend into adjacent bodies. Both
reviewers independently identify the earlier return/tail-jump boundaries. The
corrected selected body ends include their delay slots. Preliminary windows stay
retained and labeled; their adjacent methods are not attributed to these targets
or analyzed further. No additional target/callee body is opened to explain them.

Independent word decoding and bounded static objdump agree: the dispatcher accepts
first argument one or zero and second argument 65535, otherwise returns. It
replaces a0 with `0x09E7D380` and tail-jumps to the selected initialization or
zero-flag target. Its conditional branches and tail jumps have NOP delay slots.
The previously inspected wrapper supplies `(1, 65535)`, selecting initialization.
This does not establish that the zero-flag path is actually invoked by a teardown
loader or that all callbacks have the same convention.

The initialization target saves this in s0, calls `0x09C344C0`, then writes
`0x09E7D208` into this+0 and returns. The zero-flag target writes the same value
then tail-jumps to `0x09C34508`. These external callees remain uninspected.
The shared object address equals original stored-image end / declared BSS start;
the image has 128 BSS bytes, not a proven 128-byte class instance.

The bounded 56-byte data window `0x09E7D200..0x09E7D238` has SHA-256
`b3f7659a4b09ebb83ffbdd649b5c890b125bb6162fa19457f69de431ccfe3084`.
It contains two zero words followed by twelve address words; the stored address
point at `0x09E7D208` selects the first, `0x09E7D084`. This supports a virtual-table
interpretation in the observed constructor/cleanup pattern. Other entries remain
uninterpreted; no extra methods are decoded. The zeros do not prove an RTTI flag,
ABI exclusivity or a recovered class declaration.

The retained 3,519-byte `cpp-fingerprints.json` verifies SHA-256
`91089e4d4e13ae79f6c08cdedaf9a22067ba240aa9f69e9e3ed4643fb85f5329`.
All three exact extracts, the preliminary windows and the bounded data extract
match the recovered original bytes and report identities.

identifier, priority handling and generation-function names. They agree with the

observed default-priority dispatch is therefore GNU-compatible producer evidence,
not merely folklore about a constructor-like function. No compiler is invoked to
test exclusivity or exact generated bytes in this bucket.

The CRT objects contain `__CTOR_LIST__`/`__CTOR_END__`, corresponding destructor
markers and `__dso_handle`. Their four-byte .ctors/.dtors contents are FFFFFFFF
in crtbegin and 00000000 in crtend. Those generic sentinel conventions differ
from the original explicit-bounds forward caller with no sentinel checks. Do not
identify that loader helper as a copied GNU CRT routine from these names alone.

Bounded archive parsing finds 25 ELF members in libsupc++.a, all with the package
comment `GCC: (GNU) 3.3.3+allegrex-2.2.2-psp-1.7.1`. Symbol records include the

This identifies the available comparison runtime's provenance, not its exact
presence/version or compilation flags in the game. No runtime body is newly
disassembled or executed.

## Runtime-only explanation and producer limits

All three exact terminated runtime names found by the primary in EBOOT also occur
in archive member tinfo.o, in distinct `.gnu.linkonce.r._ZTS...` sections:

| Name | Original EBOOT file offset / allocated VA |
| --- | --- |
| `St9type_info` | `0x169444` / `0x0896A790` |
| `N10__cxxabiv117__class_type_infoE` | `0x169460` / `0x0896A7AC` |
| `N10__cxxabiv120__si_class_type_infoE` | `0x169490` / `0x0896A7DC` |

These original names lie in allocated non-executable .data and follow pointer
words, so requiring a preceding NUL would wrongly miss valid names. Their exact
bytes plus terminating NUL are verified. All 355 frozen overlay payload hashes
reproduce, and none contains these three exact terminated names. This limited
query inventory does not establish that all other language/ABI evidence is absent.

A standard ABI/runtime component can explain the three names without proving the
compiler of each game unit. No new SDK/third-party library ownership is assigned.
The original main ELF separately retains the exact comment
`MW MIPS C Compiler (2.4.1.01)` followed by `PSP`; this remains producer/link-stage
metadata of uncertain origin. The particular prefix queries do not search `MW
MIPS`, so their three hits cannot be presented as absence of Metrowerks metadata.
Neither this comment nor the GNU-compatible dispatcher proves exclusive frontend
ownership, a compiler version or one global build profile.

The sampled unit now supports readable C++ static-object initialization/cleanup
more concretely than the earlier bare callback range. Original class names,
complete layout, historical compiler and precise flags remain unknown. The
parked archive initializer and all four drafts stay unchanged. No compiler/game
runs, source rewrite, match credit or port work occur. The last full regression
result remains 340 WSL tests passed, zero skipped, from 3U; no test suite is rerun
for these read-only findings.
