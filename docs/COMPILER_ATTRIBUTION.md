# Compiler-family attribution limits

Bucket 3D, 2026-10-30. The accepted executable contains Metrowerks-formatted
metadata. It does not identify the compiler of every unclassified function,
prove an original language, or lock a build/configuration. This bucket compares
one preselected PSP GCC candidate, one PSP SNC candidate and the existing
Metrowerks 219 control using only the original frozen fourteen-probe bench.

## What the accepted ELF establishes

The pinned ELF, SHA-256
`755e5d84262c3bb30635b32deffab11a66de118f501e4ac105f503308be8b950`,
has `ET_EXEC` type and raw `e_flags = 0x10A23001`. Its `.comment` consists of
the NUL-terminated strings `MW MIPS C Compiler (2.4.1.01)` and `PSP`.
These are direct observations, supporting investigation of Metrowerks toolchain
involvement somewhere in construction of the linked image.

The final build-219/O2 compiler output is `ET_REL`, has
`e_flags = 0x10970001`, and contains `MW MIPS C Compiler (3.0.0)`. Its complete
object hash is
`45d897dee18a5ddc6898a65d0963423dcb81ef2461d49808585c7b3a6f71473a`.
Comparing that relocatable object directly with the game's linked metadata does
not establish a compiler-version mismatch: the construction stages differ.
No candidate linked executable has been reconstructed in this investigation.

The bit names used by a modern ELF reader are not original command-line flags.
For example, [GNU's MIPS ELF definitions](https://github.com/pspdev/binutils-gdb/blob/febbfd5154af3d28d5e0f39fd0b9b6895f78c25a/include/elf/mips.h)
describe architecture, ABI, CPU-variant and noreorder masks. A noreorder bit does
not mean that all compiler optimization or delay-slot scheduling was disabled.
Processor-variant assignments also differ across tool implementations and time:
[GNU's Allegrex addition](https://sourceware.org/pipermail/binutils/2023-March/126815.html)
uses a distinct CPU variant from the raw field observed here. Preserve the
original integer rather than treating a modern decoder's CPU label as a reason
to change the proven PSP target or choose experimental flags.

## Is the 2.4.1.01 string generated by the linker?

A primary project report supplies a useful counterexample to reading the label
as a compiler executable's version. The
[Monster Hunter 2 project's own account](https://github.com/Batenkaitos-dev/mh2-decomp/blob/3e039431887cb925ad583c6442f57d3b3c465e43/README.md#how-it-matches)
reports the same `2.4.1.01` string in its PS2 boot executable and in the bundled
`mwldps2.exe`, while its `mwccps2.exe` reports `3.0.0`. That is the project's
direct tooling observation, not a wiki assertion. It demonstrates why a linked
banner and compiler version cannot automatically be equated.

The example is PS2, not PSP. It does **not** prove which PSP tool wrote our
string, its exact version, whether an input object's comment was retained, or
how a PSP linker would handle mixed-family input. No manufacturer PSP linker
specification or controlled PSP linking result establishing those details was
found in this bounded review. The origin of this PSP linked-stage string remains
unresolved; attributing it categorically to either compiler or linker would
overstate the available evidence.

Selection was recorded before help or scoring in

`psp-gcc-1.7.1`, `pspsnc_1.2.7503.0`, and the existing

review executes no compiler and modifies no flags or sources.

The candidate's actual `gcc-version.txt` identifies
`3.3.3+allegrex-2.2.2-psp-1.7.1`, configured with target `psp` and C/C++ support.
Driver/backend help documents C selection, object output, `-nostdinc` and target
option syntax. Driver help reports missing `pspspecs`; the matrix therefore uses
the unmodified backend with the explicit profile below, not an assumed complete
SDK driver environment.

The actual initial SNC help identifies `pspsnc 1.2.7503.0`, documents object
output via `-c`/`-o`, optimization syntax `-ON` with O0 none and O5 maximum,
and `-GSIZE` with zero disabling small-data optimization. Full-help topic/control
requests abort on wibo's missing `GetOpenFileNameA` import; they are not successful
documentation queries or evidence for undocumented options.

The invented SNC smoke's recorded driver trace supplies narrower empirical
defaults: its `.c` input uses `-XYc=mixed+gnu_ext`, defines `LANGUAGE_C`, PSP and
little-endian/MIPS macros, and invokes `pspas` with `-G0`. Those observations
describe that invocation, not the historical game's language/flags. Smoke outputs
are provisioning evidence; final object metadata and scores are separated below.

Optimization labels 0–3 are controlled inputs per family, not promises that the
families perform equivalent transformations. A documented compile-only C profile
is an experiment; it does not select the historical game's C/C++ mode, ABI
switches, optimization level or linker.

## Reviewed execution profiles

`config/compiler-families.json` records one profile per family, each applying
O0, O1, O2 and O3 to the entire unchanged bench. All three preparation smokes
can produce objects. The profile file pins binaries, support files, host runtime
dependencies and pre-score evidence; independent freeze review precedes target
scoring. The GCC driver itself is not used for the matrix.

| Family | Fixed execution profile outside its optimization level |
| --- | --- |
| GCC | Native `cc1`: `-quiet -nostdinc -G 0 -march=allegrex -mtune=allegrex -mel -mabi=eabi`; modern pinned GNU assembler: `-EL -march=allegrex -mabi=eabi -G0 -O0`. |
| SNC | Unmodified driver through wibo: `-c -G0`, with C selected by the `.c` input and confirmed by the recorded driver trace. |
| Metrowerks 219 control | Existing unmodified compiler through wibo: `-nostdinc -lang c -c`. |

The GCC archive's own `specs` has a `subtarget_cc1_spec` selecting Allegrex
generation/tuning and zero small data, `asm_abi_default_spec` selecting EABI,
and `endian_spec` selecting little endian by default. The explicit backend
profile uses those values rather than guessing from the game's header. Native
Linux temporary staging avoids the legacy 32-bit backend's file-stat overflow
on the shared Windows filesystem, keeping exact source bytes and basename.
This is a documented preparation method, not a changed compiler binary.

The GCC assembler is a modern diagnostic component rather than the unavailable
original SDK assembler. Its fixed `-O0` setting is configured for assembly
preservation; it is independent of the four frontend optimization levels and
does not disable their scheduling. An invented explicit-nop fixture passes its
narrow preservation check in `assembler-preservation.json`. That fixture does
not prove every historical assembler behavior, pseudo-instruction expansion,
linker rule or complete pipeline. GCC results therefore identify this stated
backend/assembler combination, not a reconstructed historical toolchain.

SNC's default SDK include paths are unused by the header-free bench; no
undocumented include-disable switch is added. Its unavailable GUI help topics
remain a limitation, while the supported CLI and actual driver trace document
the switches used. No candidate was substituted and no source-dependent flag
was introduced.

## Ownership and mixed-toolchain hypotheses

All fourteen probe intervals remain unclassified as game, SDK or third-party
code. The prior caller review identifies SDK import interfaces near the two
networking-related probes; it does not identify the local wrapper's producer.
SDK and middleware objects could have been compiled separately from game units,
but mixed compiler families in this executable have not been demonstrated.

An exact byte sequence establishes that the stated source/profile/candidate can
emit that bounded interval. It does not identify the original source, prove
ownership or attribute unrelated units. A non-exact sequence rejects that tested
combination for exact emission of the current draft; it does not exclude the
family for every possible original source or configuration. Broad compiler
attribution requires stronger unit/library provenance and linking evidence.

## Like-stage comparison and results

The final reports are `evidence/bucket-03d/final-reviewed-family-run-1.json` and
`final-reviewed-family-run-2.json`. They are byte-identical, 79888 bytes, SHA-256
`207ca372b08148174434555111886a0d48cf20e74fa95a278add8c0596b745b2`.
Fresh object directories are `build/compiler-families-ccyz2g6z` and
`build/compiler-families-uqp5ae_2`, with twelve objects each. The source author
checked all twelve object hashes in the first directory against the final
report before recording their metadata. Earlier development/reporting variants
are superseded and are not the final score evidence.

| Family/profile | O0 | O1 | O2 | O3 |
| --- | --- | --- | --- | --- |
| GCC | Object generated; no score | 0/14 exact | 1/14 | 0/14 |
| SNC | 0/14 exact | 0/14 | 0/14 | 0/14 |
| Metrowerks 219 control | 1/14 exact | 6/14 | 6/14 | 1/14 |

The reporting unit is a complete fourteen-probe configuration. All twelve
declared configurations were attempted; eleven fully validate and provide 154
full-symbol comparisons per run. GCC O0 has **no score**, not zero matches:
its output is rejected by the supported relocation policy. GCC O1, O2 and O3
each independently validate all fourteen complete symbols with the unchanged
comparator. No failing function is skipped to manufacture a partial score.
The original source and the profile file, SHA-256
`cb0b3fbd1961380c8cee61a286bce723be7ed13c73e39bd8c949e6c701413dab`,
remain frozen. This research reporting rule does not relax the future full-game
build gate.

Direct inspection finds nine `R_MIPS_26` records in GCC O0 `.rel.text`, all naming
the local section symbol (empty name, symbol index 2, `STT_SECTION`, section 1,
value zero). All nine affect J instructions, not named external JAL calls. The
narrow named-external-call handling from Bucket 3B does not resolve this
defined-section/addend case. No relocation word is masked or
silently treated as final. The object also contains fourteen non-code
`R_MIPS_32` records in `.rel.pdr`; they are a separate metadata observation,
not the reason to invent target-code scores. This candidate compiles at every
declared level; only its O0 configuration remains unscored under the current
supported relocation handling.

At the same relocatable-object stage, observed metadata is:

| Object producer | Raw flags | `.comment` |
| --- | --- | --- |
| GCC, all four objects; O0 unscored | `0x10843001` | GCC version string `3.3.3+allegrex-2.2.2-psp-1.7.1` |
| SNC, all four levels | `0x10A23001` | No `.comment` section |
| Metrowerks 219, all four levels | `0x10970001` | `MW MIPS C Compiler (3.0.0)` |

SNC's flags equal the linked reference's integer despite none of the fourteen
frozen probes being exact. This directly demonstrates why metadata compatibility
must stay separate from instruction equality. For example, SNC/O2's byte test
is twelve bytes rather than the target's sixteen because the zero/nonzero
conversion occupies the return delay slot. Its byte-clear store similarly
occupies that slot (eight bytes versus twelve). Its constant-return function is
eight bytes versus twelve, schedules the constant into the return slot, and uses
an OR-immediate encoding rather than the target's add-immediate encoding. The
longer loops also differ in registers, branch-likely use and scheduling. These
are actual complete-symbol differences, not reasons to trim or ignore bytes.

GCC O2's single reported exact interval is the sixteen-byte byte-copy/advance
probe at `0x08826448`. The six Metrowerks O1/O2 exact intervals are different
small controls. These observations describe each stated source/profile pair;
they must not be pooled into a mixed-family score or used to rank historical
compiler families. They do not demonstrate that the original executable mixed
compilers: the reconstructed source/types are hypotheses and probe ownership is
unclassified. Nor do they exclude SNC as the producer of unrelated or separately
compiled code. The Metrowerks banner remains useful evidence, but uniform family
ownership and an exact historical build/flag set are unproven.

A later bounded relocation-validation slice could make the same fixed GCC O0
input comparable; that requires its own review and tests. No further candidate,
profile sweep or source iteration follows automatically from this result. No
source-hypothesis variant, new game function, added overlay, runtime test or full
reconstruction is included, and the toolchain remains unlocked.

### A concrete new method: inspect the compiler's own stages

The public [MWCCPS2 debugger](https://github.com/Raikaru/mwccps2-debugger/tree/5ea1631d07e62d1aa48cf28b373a1c6315be665b)
captures internal IR, optimization boundaries, register allocation and scheduling
for exact supported PS2 executables. It checks direct versus instrumented object
identity. Its profiles do not support our PSP binary; addresses, internal layouts,
host/runner support and stage semantics cannot be transplanted by assumption.
The project is a method lead, not a newly discovered PSP compiler or ready tool.

A bounded static read of our unchanged MW219 EXE found **20 diagnostic strings**
relating to IR optimization, common-subexpression removal, copy propagation,
macro expansion, scheduling and post-coloring operations. The executable still
has SHA-256 `828f9b30b3ae33c7a0202c2baf48aab49884c60e48c5b3daa2436bc3237368df`.
This supplies concrete anchors for a feasibility investigation. String presence
alone does not prove reachable hooks, execution order, O2 pass activation or the
cause of the five repeated base calculations. Recorded file offsets are not
validated runtime addresses. No compiler, debugger or game was executed for
this observation, and no binary or configuration was changed.

The static observations, pinned public README and source identity are retained
in `evidence/compiler-search-beyond-catalogue/`. A future approved feasibility
slice could map anchor references and evaluate capture through the existing
working runner. Any later instrumented compile would need complete byte identity
with an ordinary unmodified invocation before its trace could be used as evidence.
No trace or instrumentation neutrality result currently exists for PSP.

### Broaden attribution beyond one initializer

Compiler identification should draw on several independent structural clues:
actual C++ runtime/RTTI layouts where present, constructor/guard conventions,
nonleaf calls, switch lowering and surrounding unit context. Original game code,
linked SDK/runtime/middleware and linker metadata need separate provenance.
RAD's own history records a PSP Bink compiler/linker transition to GCC in January
2009, demonstrating a real period middleware toolchain change. It supplies no
GCC version and does not establish Bink in MHP3.
[RAD history](https://www.radgametools.com/bnkhist.htm).

The Tag Force 5 project's own account also describes a larger loop separating
optimization settings that its simple functions could not distinguish. This is
a useful warning about tiny-control attribution, not evidence for copying its
flags or accepting its reported matches under our stricter gate.
[Project's account](https://github.com/angelof-exe/ygo-tf-5-decomp/blob/main/docs/06-splitting-and-matching.md).

Recommended change in approach: maintain the wider tool-package search, but
prioritize compiler-stage feasibility and a small set of independent original
code fingerprints. Do not treat the archive candidate's type/volatile/member
representation or its fixed diagnostic O2 setting as proven original choices.
No settings, source shapes, toolchain lock, next implementation bucket or
matching credit are authorized by these research findings.
